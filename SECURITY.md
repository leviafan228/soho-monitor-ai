# Безпека SOHO Monitor AI

## Повідомлення про вразливість
Не створюйте публічний issue. Напишіть автору напряму (контакт у профілі GitHub) з описом і кроками
відтворення; відповідь — протягом 3 робочих днів.

## Що захищаємо
- облікові дані користувачів і токени сесій;
- токен Telegram-бота та рядок підключення до БД;
- перелік об'єктів клієнтів (IP-адреси, назви, провайдери) і журнал інцидентів.

## Реалізовані заходи
| Загроза | Захід |
|---|---|
| Несанкціонований доступ до API | JWT (8 год), усі маршрути, крім `/api/health` і `/api/auth/login`, вимагають токен |
| Підвищення привілеїв | ролі viewer / operator / admin, перевірка ролі на бекенді для кожного маршруту (не лише приховування кнопок у UI) |
| Підбір пароля | обмеження 5 невдалих спроб / 15 хв на IP+email, однакова відповідь для «немає користувача» і «невірний пароль», аудит LOGIN_FAILED / LOGIN_BLOCKED |
| Витік паролів з БД | лише scrypt-хеш із сіллю, порівняння за сталий час; хеш не повертається API |
| Слабкі паролі | політика: ≥ 10 символів, великі та малі літери, цифра |
| Ін'єкції / XSS | валідація всіх полів (довжина, формат IP, перелік типів, заборона `< > { } $`), React екранує вивід |
| Секрети в репозиторії | `.env` у `.gitignore`, у репозиторії лише `.env.example`; сервер не стартує без надійного JWT_SECRET |
| Секрети в логах | маскування полів password / token / secret / authorization і токенів Telegram |
| Розкриття технологій і стеку помилок | вимкнено `X-Powered-By`, клієнт отримує загальну помилку, деталі — лише в лозі |
| Clickjacking / MIME sniffing | `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` |
| Небажані джерела запитів | CORS дозволено лише для адреси фронтенду (CORS_ORIGIN) |
| Втрата даних | резервне копіювання з перевіркою цілісності (див. DEPLOYMENT.md) |

## Журналювання
- `logs/app.log` — технічний лог (JSON), без секретів;
- колекція `auditlogs` — дії користувачів: вхід, невдалий вхід, блокування, додавання/видалення
  роутера, зміна налаштувань, експорт, запуск сценаріїв. Зберігається 180 днів, переглядає лише admin.

## Відомі обмеження прототипу
- немає HTTPS «з коробки» — у продакшні потрібен зворотний проксі (nginx / Caddy) з TLS;
- токен зберігається в sessionStorage (зникає після закриття вкладки); для продакшну краще httpOnly-cookie;
- обмежувач спроб входу зберігає стан у пам'яті одного процесу;
- немає двофакторної автентифікації для адміністратора.

## Реагування на інциденти безпеки (коротко)
1. Зафіксувати час і ознаки (аудит, лог), не видаляючи доказів.
2. Обмежити шкоду: заблокувати обліковий запис (`active: false`), змінити JWT_SECRET (усі сесії стають недійсними).
3. Якщо секрет потрапив у Git — **відкликати** його (новий токен у @BotFather, новий пароль БД), потім видалити з історії.
4. Відновити дані з резервної копії, якщо їх змінено.
5. Описати інцидент і запобіжні заходи в issue з міткою `security`.
